# Neon production database initialization

This procedure targets the existing Neon Free primary branch and an empty application database. Use the local Production rehearsal for write tests. Running initialization, creating roles, copying seed data and configuring hosted secrets are separate release actions.

## Inspect the target

1. Confirm the organization plan, project region, PostgreSQL major version and primary branch with `neon orgs get`, `neon projects get` and `neon branches list`. Verify the endpoint belongs to that branch. Confirm the database and its owner with `neon databases list` and `neon roles list`. The branch name, database name and hostname are different identifiers.
2. On a trusted machine, configure a protected libpq service and password file outside the repository. Use the exact direct endpoint from `DATABASE_URL_UNPOOLED`, port 5432, `sslmode=verify-full`, `sslrootcert=system` with libpq 18, `channel_binding=require` and `connect_timeout=15`. If the client has no populated CA store, use the [public CA documented by Neon](https://neon.com/docs/connect/connect-securely) as `sslrootcert`. Keep passwords out of shell history, terminal output, connection-string arguments and logs.
3. Run `PGSERVICE=fleetflow-owner psql -X -w -v ON_ERROR_STOP=1 -f deployment/inspect-postgres.sql`. It opens a read-only transaction, lists catalog metadata and migration IDs, and rolls back. Expect the `public` schema, no application tables, no EF history and no FleetFlow role names on a fresh target. Stop on unexpected application objects or ownership. Verify TLS on the client. The backend `pg_stat_ssl` view can report `ssl=false` when the managed proxy terminates the verified client TLS session.
4. Confirm the authenticated owner owns the target database, can create in `public`, can create schemas and has `CREATEROLE`. The initial Neon owner has managed `neon_superuser` membership with administrative privileges and is still a non-superuser PostgreSQL login. Keep that credential in manual release storage. Do not use the default Console/API administrative role creation for restricted application accounts. [Neon role and SQL privilege model](https://neon.com/docs/manage/roles).

## Roles and grants

The source of the executable grants is [PortfolioInitializer.cs](../backend/src/FleetFlow.Infrastructure/Portfolio/PortfolioInitializer.cs). The two permission groups are `NOLOGIN`, have no parent roles and own no application objects. SQL-created service logins use `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, inherit only their own group, and receive no grant/admin option. The initializer removes `PUBLIC` CREATE on the public schema and default `PUBLIC` execution on the reset and copy functions.

| Principal | Required access |
| --- | --- |
| Existing migration owner, `neondb_owner` on the prepared project | Owns the database/application objects. Creates and alters the EF tables, indexes, constraints, sequences, triggers, fixed schemas, and maintenance functions. Uses `CREATEROLE` for the one-shot SQL login/group setup. Keep outside the web runtime. |
| `fleetflow_web` via `fleetflow_portfolio_runtime` | `USAGE` on `public`, Viewer and configured Dispatcher schemas. `SELECT` on Viewer logistics. In Dispatcher schemas, `SELECT, INSERT, UPDATE` on Drivers, Vehicles and Shipments and `SELECT, INSERT` on Customers and ShipmentEvents. No access to the template or unscoped public logistics. |
| Runtime shared tables | `SELECT, UPDATE` on `AspNetUsers` for Identity state/stamps; `SELECT` on the other Identity tables; `SELECT` on catalog, EF history and lease slots; `UPDATE ("LeaseId","ExpiresAtUtc","Ready","Writes")` on slots. `SELECT, INSERT` on `DataProtectionKeys`. `USAGE` on `ShipmentNumberSequence` and `DataProtectionKeys_Id_seq`. |
| Runtime AI ledger | `SELECT, INSERT, UPDATE, DELETE` on `AiAttempts`; the service uses DELETE only for retention of attempts older than 30 days. That SQL grant is table-level; application code supplies the retention predicate. Sandbox cleanup cannot alter the ledger. |
| `fleetflow_maintenance` via `fleetflow_portfolio_maintenance` | `USAGE` on `public` and `EXECUTE` on `public.portfolio_prepare_slot(integer,uuid,timestamptz)`. No direct table access, sandbox schema usage, copy helper execution, table ownership, DDL or trigger control. |

The web process opens the maintenance connection only in the dedicated Dispatcher lease-preparation path. Its sole app-owned callable function validates slot, current lease UUID, expiry and pending status, locks the slot, derives the fixed schema and resets that schema only. The owner-backed function can truncate only the five tables of that sandbox. Normal runtime SQL and arbitrary HTTP routes cannot invoke it. Both secrets still reside in the same process; this is a PostgreSQL privilege boundary, not protection against full web process compromise. The shared runtime login can access all configured Dispatcher schemas. HTTP tenant isolation uses the validated lease and fixed server-selected schema, with same-schema foreign keys. It is not per-visitor PostgreSQL credential isolation.

## Approved execution order

1. Record the exact reviewed Git SHA with all five quality checks green, project, branch, direct hostname, database, and chosen slot counts (defaults ten Viewer and three Dispatcher). Recheck Free plan allowances and backup/recovery. Rehearse the reviewed image against fresh local PostgreSQL 18 and run the [approved Neon branch verification](neon-branch-verification.md) before production. Branch deletion requires its own approval. Review migration SQL via `dotnet ef migrations script --idempotent` with the explicit `FleetFlowDbContext` and the Infrastructure/API projects. Do not execute that script as an additional migration path.
2. Prepare a dedicated, backed-up production Data Protection PFX with its private key, and keep the export password in a separate secret store. Never use the branch rehearsal PFX or log any XML/key material. Build a private initialization environment using [deployment.md](deployment.md) and the two placeholder templates. It needs the direct migration-owner connection, the proposed runtime and maintenance connections with different generated passwords of at least 24 characters, the PFX path and export password, the exact HTTPS origin and allowed host, and the intended slot settings. Decode URI fields before building Npgsql keyword-value strings and use an Npgsql connection string builder or correctly quote password values. Prepare a separate runtime environment that contains the runtime and maintenance logins, never the owner. Set `AI_ENABLED=false` in both. The local development env, test credentials and any local database dump are outside this procedure.
3. Verify the read-only production baseline again and record an encrypted, restorable pre-change backup and the recovery procedure. After explicit production approval, run one reviewed image with `sh scripts/initialize-portfolio.sh --confirm-database neondb --confirm-host EXACT_PRODUCTION_DIRECT_HOST` and the private image/env/certificate settings described in [deployment.md](deployment.md). Prefer this controlled local executor. Before opting into the protected manual GitHub workflow, require the selected SHA to be reachable from protected `main` and verify each of the five successful jobs before making secrets available. Its current `github.ref` check covers the dispatch ref, while the selected SHA has only an aggregate CI-result check. Use one executor.
4. EF applies the following migrations in order. The initializer holds its own advisory lock across the migration and portfolio initialization phases.

   | Migration | Result |
   | --- | --- |
   | `20261106161244_InitialDomain` | Logistics tables, shipment sequence, constraints/indexes and append-only ShipmentEvents trigger. |
   | `20261107140050_AddIdentitySessions` | ASP.NET Identity tables and role records, and the Data Protection key ring table. No user passwords are seeded. |
   | `20261108214714_AddAiUsageLedger` | Persistent attempt/budget/cache ledger. |
   | `20261109141046_AddPortfolioLeases` | Adds `IsDemo` and bounded lease slots with unique Identity links. |

5. The initializer transaction creates `PortfolioCatalog`, fixed template/Viewer/Dispatcher schemas, their same-schema foreign keys and audit triggers. It generates source-defined fictional records in the template and copies them into demo schemas. It creates only bounded passwordless demo identities and grants. It does not read a development database or copy development users, passwords, key XML, or AI usage. Runtime and maintenance SQL logins are provisioned together in a separate transaction. An existing password is retained on rerun.
6. Check all four migration IDs, the catalog revision and the expected slots/schemas. From a separate read-only session as each service login verify membership, grants, ownership, allowed function signature and no effective DDL on application schemas. Prefer `has_table_privilege`, `has_schema_privilege`, `has_function_privilege` and `pg_has_role` catalog checks in production. Run destructive denial/rollback cases only against local disposable PostgreSQL. Record zero initial business rows in the normal public tables and zero initial AI attempts.
7. After separate approval for hosting, start the image using runtime and maintenance credentials plus the same external PFX. ASP.NET Core writes encrypted Data Protection keys to PostgreSQL when first used; the initialization CLI does not seed the key ring. Verify that the ring is encrypted and survives a restart with the same certificate. Do not log the XML. Validate a session and the CSRF token across restart, sandbox isolation, and quota preservation. Keep public sharing gated on the proxy and browser checks in [deployment.md](deployment.md).

A retry after a failed role transaction leaves neither a partial new login nor partial group grants. A seed transaction failure can leave successful EF migrations in place. Inspect the target before retrying. Once slots exist, initialization checks that all applied EF migrations match the build and the catalog before allowing a repeat; schema drift requires a reviewed upgrade. Do not downgrade an initialized portfolio database. Changes to initial pool size, grants on already initialized databases or fixed schemas require a reviewed follow-up change. Do not re-run with a different service login name as an implicit rotation. See [recovery and certificate rotation](deployment.md#backup-and-recovery).

## Remaining privilege review

- **AI attempt retention.** The current web role can delete any ledger row, including today's quota records. Its application path prunes rows with `DayUtc < UTC today - 30 days` on reservation. Keep AI disabled for initial launch. Before enabling it, remove pruning from the reservation path, revoke runtime `DELETE` and run retention as a separate manual operation. If automated pruning is later needed, grant execution on a narrowly owned function with a fixed database-computed UTC cutoff, a fixed search path and no caller-supplied predicates or target table. Grant runtime `UPDATE` only on completion, retry and cache columns, so attempts cannot be reassigned to another user or quota day. Rehearse pruning at the cutoff and prove active budgets survive both retention and sandbox reset.
- **Sandbox reset.** The separate maintenance login limits damage from exposure of either database credential alone. A compromised web process can obtain both and the runtime role can write lease metadata, so the process itself is not an isolation boundary. Keep the single-service design for launch. Harden the definer function by checking lease expiry against database time, granting a dedicated `NOLOGIN` function owner only the rights it needs, and retaining the slot fence and fixed schema allowlist. Rehearse reset, concurrent lease fencing and quota/key preservation before applying changes. A separate reset service would isolate credentials from the web process but adds operational complexity and needs its own design and approval.

## Free-tier and connection limits

Neon documents SQL-created restricted roles without a requirement for PostgreSQL superuser or a paid plan. The role/grant flow is rehearsed with a local PostgreSQL 18 non-superuser database owner with `CREATEROLE`. Actual role creation on the Neon branch must be verified after approval. [Managed PostgreSQL compatibility](https://neon.com/docs/reference/compatibility).

Current published Free allowances include 100 CU-hours per project per month, 1 GB storage per project (20 GB across Free projects), 5 GB monthly egress per project and suspension after five idle minutes. Restore history is limited to six hours and 1 GB of changes. Maintain an independent encrypted backup and review actual account consumption. Compute size affects direct connection limits. Allow one web instance, Npgsql max pools 10/2, zero minimum and no keepalive. Use `Pooling=false` for migrations. Start with a 15-second connection timeout and command timeouts of 30 seconds for runtime, 20 for reset and 60 for initialization. Size against observed cold starts and avoid unbounded retries. The Neon transaction pooler cannot hold the session advisory locks required for lease fencing. [Neon plans](https://neon.com/docs/introduction/plans), [connection pooling](https://neon.com/docs/connect/connection-pooling), [Npgsql TLS](https://www.npgsql.org/doc/security.html).
